# MindDock 性能验证方案

本文定义性能验证的统一口径、测试场景与验收输出。

目标不是提前做复杂基准测试平台，而是在规划阶段先约束：

- 什么叫“性能达标”
- 怎样测才算有效
- 哪些回归必须阻断进入下一阶段

如与 `docs/CONSTRAINTS.md`、`docs/ROADMAP.md` 冲突，以两者为准。

---

## 1. 核心原则

1. **只接受统一口径的性能结论**：没有统一测试条件的数据不作为阶段验收依据。
2. **优先测用户可感知体验**：先测输入、打开、切换、恢复，再测理论吞吐。
3. **先守住 p95，再追求极限平均值**：MindDock 的目标不是偶尔快，而是持续稳定。
4. **性能回归必须阻断扩功能**：核心指标不达标时，优先修复，不继续堆需求。

---

## 2. 指标定义

## 2.1 输入延迟

定义：

- 从 `keydown` 触发到对应 transaction 完成、DOM 可见更新结束的耗时

验收指标：

- p95 < 16ms

说明：

- 使用 p95，不使用平均值
- 连续输入场景必须纳入统计

## 2.2 打开笔记耗时

定义：

- 从用户点击 note 到编辑器进入可编辑状态的耗时

验收指标：

- p95 < 100ms

## 2.3 切换笔记耗时

定义：

- 从切换动作触发到目标 note 内容可编辑的耗时

验收目标：

- 应接近打开笔记指标
- Phase 1 先追求稳定，无需过早追求极限

## 2.4 保存反馈耗时

定义：

- 从输入停止到系统完成本地持久化，并更新为 `已保存` 的耗时

验收目标：

- 用户感知为无打断
- 数据上需记录真实分布，避免状态反馈虚快

## 2.5 恢复耗时

定义：

- 页面刷新后，从应用启动到最近编辑内容恢复可见的耗时

验收目标：

- 应足够快，不造成明显“空白后再跳出内容”

---

## 3. 测试环境口径

每轮性能验证必须记录：

- 设备型号
- CPU / 内存信息
- 操作系统版本
- 浏览器及版本
- 是否接电
- 是否使用生产构建
- 数据集规模

规划建议：

- 至少固定一台“主验收设备”
- 其他设备数据可作为参考，不作为主 Gate 判定

禁止：

- 在开发模式下用主观感受代替正式结论
- 混用不同浏览器、不同数据规模得出同一结论

---

## 4. 数据集分层

为避免“空数据快，真实数据慢”，性能测试至少使用三档数据集：

### Small

- 50 条 notes
- 每条内容较短

用途：

- 开发期快速回归

### Medium

- 500 条 notes
- 混合短中长内容

用途：

- Phase 1/2 主验证集

### Large

- 5,000 条 notes
- 含较长内容、频繁更新项

用途：

- 验证列表、搜索、启动预热策略是否退化

开放问题：

- 单条 note 最大长度要不要单独建极端测试集

---

## 5. Phase 1 必测场景

## 5.1 连续输入

场景：

- 同一 note 持续输入 10 分钟

观察项：

- 输入延迟 p95
- 是否出现明显卡顿
- 光标是否跳动
- 是否出现布局抖动

## 5.2 大段粘贴

场景：

- 粘贴较长文本到当前 note

观察项：

- 粘贴后短时卡顿
- 保存是否延后但不丢失
- 后续继续输入是否恢复稳定

## 5.3 快速切换笔记

场景：

- 多条 note 间频繁切换并继续编辑

观察项：

- 切换耗时
- 切换前 flush 是否拖慢交互
- 是否出现内容串写

## 5.4 刷新恢复

场景：

- 编辑中刷新页面，再次进入

观察项：

- 恢复耗时
- 是否恢复到最近可靠保存状态
- 状态提示是否清晰

## 5.5 离线编辑

场景：

- 断网后创建、编辑、删除 note

观察项：

- 是否影响核心交互
- 是否出现错误误报

## 6. 埋点建议

规划阶段先定义最小埋点集合：

- `input_latency_ms`
- `note_open_ms`
- `note_switch_ms`
- `save_flush_ms`
- `recovery_ms`
- `save_failure_count`

最小要求：

- 埋点采集不得进入输入关键路径做重计算
- 可先缓存在内存，调试时导出
- 生产是否持久化统计数据可后置决策

规划建议：

- 埋点实现与业务逻辑解耦
- 允许通过 debug 开关开启详细性能面板

---

## 7. 验收输出格式

每次阶段验收至少产出一份性能记录，包含：

- 测试日期
- 代码版本或里程碑标识
- 测试设备与浏览器
- 数据集档位
- 各指标 p50 / p95 / max
- 是否通过 Gate
- 若失败，定位结论与后续动作

建议格式：

- Markdown 报告
- 配套原始数据附件或截图

---

## 8. 回归判定规则

以下情况应视为阻断级回归：

- 输入延迟 p95 超过 16ms
- 连续输入出现稳定可复现卡顿
- 切换或恢复时出现内容错误
- 保存状态反馈与真实持久化状态不一致

以下情况可先记录但不阻断：

- 次级界面动画略有掉帧
- 非核心列表在极端大数据集下轻微变慢

前提：

- 不影响输入、保存、恢复主链路

---

## 9. Phase 2 / Phase 3 补充指标

## Phase 2

新增关注：

- 标签解析延迟
- 搜索首屏响应时间
- 大数据集列表滚动表现

要求：

- 标签与搜索必须证明未污染输入链路

## Phase 3

新增关注：

- 同步入队耗时
- 网络恢复后补同步耗时
- 同步失败时本地操作延迟是否退化

要求：

- 同步相关指标不得替代本地性能指标

---

## 10. 实施顺序建议

1. 先定义指标与埋点位置
2. 再建立 Small / Medium 测试数据集
3. 再补连续输入、切换、恢复三类脚本或手动流程
4. 最后把结果接入每阶段 Gate

---

## 11. 仍待决策的问题

- 输入延迟的终点以 transaction 完成还是 DOM paint 完成为准
- 是否需要录屏辅助验证光标跳动与布局抖动
- 是否建立长期性能基线历史
- 是否为不同浏览器分别设定基线

这些问题在进入正式实现前应确定第一版答案。
