# MindDock 项目现状与后续工作

本文是项目执行入口，用来回答三件事：

1. 现在做到哪了
2. 当前阻塞是什么
3. 接下来按什么顺序推进

如与 `docs/CONSTRAINTS.md`、`docs/ROADMAP.md` 冲突，以两者为准。

---

## 1. 当前状态

当前阶段：`Phase 1 / 本地编辑器`

当前结论：

- 项目方向清晰，约束定义完整
- 前端已有最小可运行骨架
- 代码结构已基本对齐 editor / data / ui 分层
- 还没有完成 Phase 1 的正式 Gate 验收

当前已落地能力：

- TipTap 编辑器可用
- 本地数据持久化到 IndexedDB
- 300ms debounce 自动保存
- 刷新后恢复最近活动 note
- 支持多 note 创建与切换
- UI 已提供保存状态和离线状态反馈

当前未完成能力：

- 输入性能埋点与正式测量
- 崩溃恢复验证
- 保存失败路径验证
- 多 tab 冲突策略
- 删除 note 能力
- 可复现的 Phase 1 验收记录

## 2. 当前代码盘点

代码入口：

- `apps/web/src/ui/EditorView.tsx`：页面薄壳、状态反馈、note 切换
- `apps/web/src/editor/setup.ts`：TipTap 初始化
- `apps/web/src/editor/events.ts`：输入后 debounce 保存
- `apps/web/src/data/repository.ts`：本地数据访问入口
- `apps/web/src/data/db.ts`：IndexedDB 定义

当前架构判断：

- 编辑器实例通过 ref 挂载，没有走 React 受控输入，这一点符合输入路径约束
- 保存动作放在 debounce 后执行，方向正确
- 但 `editor update -> debounced save -> onSaved -> setNotes(...)` 这一链路仍需要实测确认不会在高频输入时造成可感知抖动
- 当前失败处理以提示为主，还没有形成“失败注入 + 恢复验证”的闭环
- 当前 `Note` 类型与 README / DESIGN 中声明的 `createdAt` 字段不一致，文档应以“当前实现”与“目标模型”分开表述

## 3. 文档状态判断

当前文档的优点：

- 目标、约束、路线图、性能口径都已存在
- 阶段验收标准写得比较明确
- `docs/ISSUES_AND_MILESTONES.md` 已具备任务管理雏形

当前文档的问题：

## 4. Phase 1 阻塞项

进入 Phase 2 前，必须先清掉以下阻塞：

### 阻塞 1：没有正式性能数据

影响：

- 无法证明输入体验达到 `p95 < 16ms`
- 无法判断当前架构是否真的满足 Gate A

需要产出：

- 最小埋点方案
- 测试脚本或手工测量流程
- 一份可复现的性能记录

### 阻塞 2：恢复与失败路径未验收

影响：

- 无法证明“写得放心”
- 目前只有正向 happy path，缺少可靠性结论

需要产出：

- 刷新恢复测试记录
- 崩溃恢复测试记录
- IndexedDB 失败注入方案与用户提示验证

### 阻塞 3：多 tab 策略未定义

影响：

- 当前多窗口同时编辑同一 note 时存在行为不确定性
- 这会直接影响本地优先场景下的用户信任

需要产出：

- 冲突检测策略
- 最小实现策略
- 用户可见提示方案

## 5. 推荐执行顺序

建议不要立刻做标签、搜索、同步，而是先把 Phase 1 做成可验收状态。

### Track A：先完成 Phase 1 Gate

1. 建立输入性能埋点
2. 跑完 Phase 1 的连续输入 / 切换 / 刷新恢复测试
3. 补保存失败注入与恢复验证
4. 定义并实现多 tab 冲突策略
5. 形成一版正式验收记录

### Track B：补齐最小产品闭环

1. 增加删除 note 能力
2. 增加更明确的错误与恢复提示
3. 补键盘可达性检查

Track B 可以并行思考，但优先级仍低于 Track A。

## 7. 本周可执行版本

如果你希望接下来一周聚焦最关键的推进，建议按这个顺序做：

1. 做性能埋点，先拿到第一版真实数据
2. 做恢复与失败路径验证，把可靠性问题暴露出来
3. 定义多 tab 策略并实现最小版本
4. 把 Phase 1 的验收记录补完整

这样完成后，项目会从“方向正确的骨架”升级成“可进入下一阶段的可验证基础”。
