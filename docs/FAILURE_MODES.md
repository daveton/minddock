# MindDock 失败路径与恢复策略

本文定义系统在异常场景下的行为原则、用户可见反馈与恢复策略。

目标不是覆盖所有技术细节，而是在规划阶段先明确：

- 失败发生时，用户会看到什么
- 系统优先保护什么
- 哪些失败允许降级，哪些失败必须阻断

如与其他文档冲突，以 `docs/CONSTRAINTS.md` 为准。

---

## 1. 总原则

1. **优先保护用户内容**：任何异常下，首要目标是减少内容丢失风险。
2. **优先保护输入连续性**：异常反馈不得打断当前输入。
3. **禁止静默失败**：保存、恢复、同步、导出等关键失败必须有可见反馈。
4. **允许功能降级，不允许错误伪装成功**：失败时可以退回本地模式，但不能显示“已保存”掩盖事实。
5. **先本地闭环，再远程一致**：Phase 3 的同步失败不能反向破坏本地可用性。

---

## 2. 失败等级

### Level 1：可恢复降级

定义：

- 当前输入可继续
- 数据仍有本地副本
- 系统可退回简化模式

示例：

- 网络断开
- 同步失败
- 搜索索引延迟
- 标签解析失败

要求：

- 不阻断输入
- 提供轻量状态提示
- 后台自动重试或允许手动重试

### Level 2：本地可靠性受损

定义：

- 当前输入仍可继续，但本地持久化能力异常
- 用户内容存在丢失风险

示例：

- IndexedDB 写入失败
- 浏览器存储配额不足
- 本地数据库升级失败

要求：

- 明确告知“当前内容未可靠保存”
- 提供可执行恢复建议
- 阻止系统错误显示为“已保存”

### Level 3：核心能力阻断

定义：

- 用户无法可靠编辑或恢复核心内容

示例：

- 数据库损坏导致无法读取最近内容
- 编辑器初始化失败
- 恢复流程读到无法解析的内容结构

要求：

- 显示阻断级错误界面
- 提供恢复路径或导出原始数据入口
- 保留诊断信息，便于后续修复

---

## 3. 关键失败场景

## 3.1 自动保存失败

触发条件：

- debounce 保存触发后，写入 IndexedDB 失败

系统行为：

- 当前编辑状态保留在内存
- 停止显示 `已保存`
- 显示 `保存失败` 或 `未可靠保存`
- 允许后台重试

用户反馈：

- 轻量但持续可见
- 不使用瞬时 toast 作为唯一反馈

恢复策略：

- 自动重试最近一次待保存内容
- 用户切换 note 前必须先尝试 flush
- 若持续失败，提示用户导出当前内容

禁止：

- 写入失败后仍显示 `已保存`
- 因一次失败就清空当前编辑内容

---

## 3.2 页面刷新或浏览器崩溃

目标：

- 尽可能恢复最近一次已落地内容
- 明确区分“已恢复内容”与“可能丢失最近若干输入”

系统行为：

- 启动时加载最后编辑 note
- 若存在最近恢复上下文，则优先恢复
- 恢复后显示轻量提示，例如 `已恢复上次编辑内容`

规划约束：

- Phase 1 以 debounce 持久化为基础
- 需补充页面隐藏、失焦、关闭前的强制 flush 策略

开放问题：

- 是否额外维护 crash snapshot
- snapshot 与正式 note 保存是否分离

---

## 3.3 切换笔记时保存未完成

触发条件：

- 用户在 debounce 窗口内切换 note

系统行为：

- 切换前触发一次立即 flush
- flush 成功后切换
- flush 失败时不应静默切换并假装成功

推荐策略：

- 默认阻止无提示切换
- 提示用户当前内容未可靠保存
- 允许用户选择重试或继续切换

规划建议：

- Phase 1 优先保证正确性，而不是“无感切换”
- 切换时最多容忍一次短暂状态提示，不做复杂弹窗

---

## 3.4 IndexedDB 不可用或配额不足

触发条件：

- 浏览器禁用本地存储
- Safari/隐私模式限制
- 存储空间耗尽

系统行为：

- 启动时探测本地持久化能力
- 若不可用，明确进入受限模式
- 若运行中失败，升级为 Level 2 错误

用户反馈：

- 明确说明“本地保存不可用”或“存储空间不足”
- 提供建议，例如清理空间、切换浏览器、导出内容

规划建议：

- 不把“仅内存模式”定义为默认可接受状态
- 仅在用户明确知情时允许临时继续编辑

---

## 3.5 多标签页同时编辑

这是本地优先笔记系统的高风险场景，必须在规划阶段先定规则。

建议默认规则：

- Phase 1 不承诺同一 note 的多 tab 实时一致
- 允许检测到冲突风险后给出提示
- 后打开的 tab 若发现已有活动编辑会话，应进入只读提醒或冲突警告状态

最低要求：

- 不允许静默覆盖
- 必须能识别“本地内容已被其他窗口更新”

后续演进：

- 引入 `revision`
- 使用 `BroadcastChannel` 或类似机制做会话协调

---

## 3.6 搜索或标签索引失败

适用阶段：

- Phase 2

系统行为：

- 不影响编辑与保存
- 仅影响组织能力

用户反馈：

- 可显示 `索引延迟` 或 `搜索结果可能不完整`

要求：

- 标签/搜索属于后台能力
- 失败后允许重建索引
- 不得阻塞输入主链路

---

## 3.7 同步失败

适用阶段：

- Phase 3

系统行为：

- 本地继续可编辑
- 失败项进入 sync queue 重试
- 明确区分“本地已保存”和“远程未同步”

用户反馈：

- 显示 `同步失败`，但同时说明本地内容仍安全

最低规则：

- 同步状态不可覆盖本地保存状态
- 不得因远程失败锁死本地 CRUD

---

## 3.8 数据结构升级失败

触发条件：

- IndexedDB schema migration 失败
- 新版本无法兼容旧数据

系统行为：

- 阻止继续进入不确定状态
- 显示明确错误页
- 提供诊断信息与可选恢复方案

规划要求：

- 单独补充 `docs/DATA_MIGRATION.md`
- 每次 schema 变更必须写升级与失败回退方案

---

## 4. 状态文案约束

为避免误导，状态文案必须区分以下语义：

- `已保存`：内容已可靠写入本地持久化层
- `保存中`：有待持久化内容，仍在尝试写入
- `保存失败`：最近变更未可靠落地
- `离线编辑中`：网络不可用，但本地仍可编辑
- `同步失败`：远程失败，不代表本地丢失

禁止混淆：

- 不得用 `已同步` 代替 `已保存`
- 不得用 `离线` 暗示保存失败
- 不得在未知状态下显示成功语义

---

## 5. 恢复优先级

当系统需要在多个目标之间取舍时，优先级如下：

1. 保住用户最新内容
2. 保住本地可编辑能力
3. 保住列表、标签、搜索等次级能力
4. 保住远程同步一致性
5. 保持界面完整和视觉连续性

---

## 6. Phase 1 最小落地要求

Phase 1 至少需要明确并实现以下失败行为：

- 自动保存失败的可见状态
- 页面刷新后的恢复路径
- 切换 note 前的保存 flush 规则
- 本地存储不可用时的降级提示
- 禁止静默失败

Phase 1 可暂缓但必须在文档中明确未解决的项：

- 多 tab 冲突
- 复杂导入失败
- schema migration

---

## 7. 仍待决策的问题

- 是否引入独立的 crash snapshot
- 是否允许临时“仅内存编辑”模式
- 多 tab 的默认策略是阻止、警告还是合并
- 删除 note 是否采用软删除
- 恢复提示是自动消失还是手动确认

这些问题在进入实现前应至少冻结一版结论。
